Are my agents mostly paying to reread things?

2026-10-21

Three bookmarks from the last day or so came at the same idea from different sides. None of them is about making the model smarter. They're all about making it read less.

Reading the whole file to change one line

@goan999999 described a familiar annoyance (my translation from Chinese): ask an AI to fix a bug and it reads the whole file every time, so on a big project the tokens are gone before much code has changed. Their fix was connecting Codex to Serena, an MCP server (a plug-in tool the agent can call) that finds code by function, class, and reference instead of by dumping files. The way they split the work stuck with me: Codex does the thinking and writing, Serena does the precise locating.

They say token use dropped by about 90%. I haven't tried it, so I can't vouch for the number. But the shape of the idea makes sense to me. A person fixing a bug doesn't reread the codebase. They jump to the definition, check who calls it, and stop.

Bots that only wake up when there's work

The second one is louder. @Greshamtrade's post opens with a claim about a student running 300 Grok Bots for "less than $0.02 per bot a week," which I have no way to check, and I'm a little wary of it. What I found useful was the list of what supposedly made the difference:

"he cut empty checks, stopped rereading entire chats, and killed retry loops. most bots now wake up only when there's actual work to do"

And near the end, a one-line ordering I keep coming back to:

"filter before reading → reuse before generating → check for changes → stop failed loops"

That hit close to home. I run a couple of small bots myself, one that sorts my bookmarks and one that drafts these notes. Every morning they wake up whether or not anything happened. How much of what they do is the "empty check" kind: opening the same feed, reading the same context, finding nothing new? I genuinely don't know, and I should probably find out before worrying about which model they use.

Even the format is too wordy

The third is about output rather than input. @Ryrenz wrote about OpenUI, a project that lets a model stream a working interface instead of code you paste back in. The interesting bit is why they replaced the usual approach. Normally the model returns a big chunk of JSON, you write a parser to turn it into components, and the JSON is long, eats tokens, and streams in a jerky way. So they made a compact streaming language called OpenUI Lang. By the project's own measurements across seven interface scenarios, it uses about 52.8% fewer tokens than Vercel's json-render.

I like that it's the same instinct pointed the other way. Serena asks "does the model need to read all this?" OpenUI asks "does the model need to write all this?"

What I'm left wondering

If I put these together, the cost of an agent doesn't sit mainly in the thinking. A lot of it is ceremony: rereading files, replaying chats, checking things that haven't changed, spelling structure out in a verbose format. All three posts treat that ceremony as something to engineer away with plain old tools like search indexes, caches, and schedulers, not with a bigger model.

What I'm unsure about is the trade. Every shortcut here is a bet that the thing you skipped didn't matter. A bot that only reads what changed can miss the context that explains the change. A tool that jumps straight to one function might not see that the real bug is two files over. Maybe that's why Greshamtrade follows that ordering with "then measure completed work against total usage," not just usage. Cheaper only counts if the bot still gets the work done.

So my small experiment for this week: look at what my own bots actually read on a quiet morning, and see how much of it is just them rereading.
