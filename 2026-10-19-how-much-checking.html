How much checking does a change deserve?

2026-10-19

Yesterday I wrote about getting an agent to grill me before it opens a PR. Today I bookmarked a post that more or less answers the question I should have asked first: when is grilling worth it at all?

Don't grill a tiny diff

@mattpocockuk lays out when he uses his /grill-with-docs and /wayfinder commands and when he just lets the agent one-shot the code. The first rule is the one that stuck with me:

"If the diff is tiny, DON'T grill"

His reasoning is that grilling protects you from the agent building the wrong thing, and when the thing is tiny, building the wrong thing costs almost nothing. So you just check the result.

The second rule is the more surprising one: "Never start with /wayfinder." From the post, wayfinder is the heavier planning step, the one that makes a map and tickets. If you start there and the solution turns out to be simple, you've built planning you don't need. So he starts with the conversation, and only turns it into a map if planning "starts to get out of hand."

I like that the order is cheap first, heavy only when the work asks for it. And I notice I had it a bit backwards yesterday. I was excited about "grill me" as a habit for everything. Matt's version says the size of the change should decide how much talking happens before the code.

The check that needs no conversation

The same person posted a prompt of the day that's the opposite kind of check:

"Create a pre-commit hook that prevents files over 5,000 tokens. Tokens = bytes/4."

It only runs on staged files and skips things agents didn't write, like lockfiles and generated code. The part I keep rereading is the last line of the prompt: "Provide explicit instructions on how to split files in the error message."

So the error message is really a prompt. When the agent hits the limit, the thing that stops it also tells it what to do next. That links back to my post from a few days ago about whether rules belong in prose or in code. This is a rule that lives in code, and it still talks, but only when it fires.

I'm not sure the number matters much. Bytes divided by four is a rough guess at tokens, and 5,000 is a choice, not a law. My guess is the real value is that some limit exists and a script enforces it, so nobody has to remember it.

A job whose only task is doubt

The third bookmark is about memory rather than code, but it feels like the same question. @Argona0x describes a "second brain" built from three bots in one group chat, which the post credits to a Karpathy pattern. I'm going on the post's description here, since I haven't seen the full setup it links to.

The split is "Reader collects. Librarian writes. Checker doubts." The reader keeps sources untouched, the librarian rewrites wiki pages, and the checker runs every night looking for contradictions, stale claims, and pages nothing links to. Two details I liked:

"a new source contradicts an old page: the checker tags you instead of quietly overwriting it"

"a page goes 30 days without a fresh source: it gets marked unconfirmed"

And every page has to show the claim, the source, and the date it was last confirmed. The line that sums it up for me is "a second brain can sound sure while remembering the wrong thing."

What ties these together, I think

All three are about matching the check to the risk. A tiny diff gets no grilling. A file-size rule gets a script, because a script never forgets. And memory, which slowly goes out of date without anyone noticing, gets a separate role that exists only to doubt it, and that asks a person when it finds a conflict instead of deciding on its own.

That last part is the one I want for myself. The things I bookmark and the notes I keep go stale too, and I rarely notice. A page that says "last confirmed 40 days ago" is a small, honest thing to show.

What I can't tell yet is how much of this I'd actually keep up. Three bots and a nightly check sounds great on the first day. The post's own advice is to "start with one topic you actually work on, not your whole life," which is probably right, and is also Matt's rule again in a different setting: start small, and add structure only when you need it.
