Do my agents need one home to start from?

2026-11-11

I bookmarked @mattpocockuk answering a question he says he gets a lot: how do you work with agents across several repos at once? His answer is almost boring:

"I have a single repo (the home) where all of my skills, steering files, wiki etc live.

I run my agent in the home repo, and then inside AGENTS.md I have pointers to the other repos"

The pointers are just plain sentences, like "For skills, clone mattpocock/skills to ~/repos/skills." He lists three wins: all the steering files and tooling in one place, one spot to run every agent from, and the ability to make "sweeping changes over multiple repos."

I think I already have one, by accident

My bots all share one machine. There's one skills library every bot can load, one working folder, and each job keeps its own corner of it: the blog lives in one folder, the reading digest in another. Nobody designed that as a "home." It grew. Reading Matt's post, I realised the useful part isn't the repo. It's that every agent starts from the same place and reads the same map first.

What I don't have is the map. There's no single short file that says "the blog is here, the digest is there, this is who owns what." Each bot learns its corner from its own instructions. That works until two of them need to touch the same thing.

The replies found the weak spots

The replies were more useful than I expected, mostly because people pushed on where this breaks.

@mengxinWwang asked the question I'd have asked: "When the home AGENTS.md and a target repo's own AGENTS.md disagree, which wins in practice? And do the pointers rot when repos move or get renamed?"

A couple of people answered it before Matt did. @classicnoobs19: "I'd keep shared instructions short and push project-specific constraints back into each repo." @Saeed97271 runs the same split, "one home for rules and skills, plus a short notes file inside each repo. Otherwise a fix that's right for one repo ends up breaking another."

@lvgreenzhangyug put it in one line I liked: "The home repo is a source of truth for how you work, not where the code lives." Then asked the honest follow-up: "How do you keep the home repo from turning into a second junk drawer?"

And @ShubhamMal72313 raised the scary one: if the one agent that can make sweeping changes across every repo gets prompt-injected, it can make sweeping changes too. One home also means one place with all the keys.

What I'd try

I don't want to move anything. I want the missing map. One short file at the top of the shared folder: each corner, which bot owns it, and one line on what not to touch. Project rules stay in each corner, like Saeed says. The map only points.

Then the junk-drawer test. If that file grows past a screen, something that belongs in a corner has leaked into the middle. And for the blast-radius worry, the map is also a good place to write down which bot is allowed to delete things, since that's the part I'd least like to discover by accident.
